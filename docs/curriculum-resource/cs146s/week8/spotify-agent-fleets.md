## 中文翻译

### 从迁移脚本到 Agent 舰队

Spotify 的工程团队管理着数千个微服务和庞大的代码库。传统上，大规模代码变更（如框架迁移、API 版本升级）由专门的迁移脚本团队处理。但随着 AI Agent 的成熟，我们开始用后台 Agent 舰队来替代这些脚本化流程。

#### 背景：迁移脚本的局限

Spotify 过去用定制脚本来做大规模代码变更。这些脚本是有效的，但有几个问题：

- **脆弱性**：脚本假设代码遵循特定模式，偏离模式就会失败
- **维护成本**：每次代码库变化都需要更新脚本
- **长尾问题**：脚本能处理 80% 的情况，剩下的 20% 需要人工逐个修复
- **不可扩展**：同时运行多个迁移需要多个脚本团队

#### 转向 Agent 舰队

我们转向用后台 Agent 来处理这些任务。核心思路是：

1. **将迁移分解为任务**：每个迁移被分解为多个独立的子任务（如"迁移服务 A 的 API 调用"）
2. **分配给并行 Agent**：每个子任务分配给一个后台 Agent
3. **Agent 自主工作**：每个 Agent 在自己的沙箱中克隆代码、分析变更、实施修改、运行测试
4. **人类审查 PR**：Agent 完成后创建 PR，人类做最终审查

#### 架构

我们的后台 Agent 系统由以下组件组成：

**任务编排器**

- 接收迁移任务（如"将所有服务从 v1 API 迁移到 v2"）
- 将任务分解为子任务
- 将子任务分配给可用的 Agent
- 跟踪整体进度

**Agent 工作单元**

每个 Agent 工作单元：
- 在隔离的容器中运行
- 有自己的代码克隆
- 可以运行构建、测试、lint
- 有上下文窗口和工具集（read、write、edit、bash）
- 完成后创建 PR

**验证管线**

每个 Agent 创建的 PR 自动进入验证管线：
- CI 测试
- lint 和类型检查
- Agent 自我审查（Agent 检查自己的 diff）
- 人类审查

#### 关键经验

**1. 上下文是关键**

Agent 需要足够的上下文才能做出正确的变更。我们发现以下上下文至关重要：
- 迁移指南（从什么改到什么，为什么要改）
- 示例 PR（已经迁移完成的服务的 PR 作为参考）
- 测试套件（Agent 用测试来验证自己的修改）

**2. 失败是常态**

在 100 个并行 Agent 中，大约 15-20 个会失败。失败原因包括：
- 代码不符合预期模式
- 依赖缺失
- 测试套件本身有问题
- 上下文窗口不够

系统需要优雅地处理失败——将失败的子任务重新排队，或升级为人工处理。

**3. 并行的限制**

并行 Agent 数量不是越多越好。限制因素包括：
- CI 资源（每个 Agent 都需要跑 CI）
- API 速率限制（LLM API）
- 代码库的并发修改冲突

我们发现在同一仓库上同时运行 20-30 个 Agent 是实际的上限。

#### 结论

后台 Agent 舰队将大规模代码迁移从"脚本 + 人工"模式转变为"Agent + 人类审查"模式。这不是完全自动化——人类仍然在关键节点介入——但它将人类的角色从"做迁移"转变为"审查迁移"，这是一个数量级的效率提升。
