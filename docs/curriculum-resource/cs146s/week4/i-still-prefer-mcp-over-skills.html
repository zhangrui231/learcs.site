I Still Prefer MCP Over Skills —— 我仍然偏好 MCP 而非 Skills

中文翻译​

我仍然偏好 MCP 而非 Skills​

Agent Skills（技能）和 MCP（Model Context Protocol）是扩展编码 Agent 能力的两种主要方式。它们各有优劣，但在深入比较之后，我仍然偏好 MCP。以下是我的理由。

Skills 的优势​

Skills（通过 SKILL.md 定义）有几个明显优点：

  • 零基础设施：不需要运行服务器，只是一个 Markdown 文件加可选脚本
  • 易于分享：直接放进仓库，git 就是分发渠道
  • 渐进式披露：技能只在触发时加载正文，不占用常驻上下文
  • 人类可读：任何人都可以打开 SKILL.md 阅读和理解工作流

这些优势使得 Skills 非常适合编码工作流类的任务——比如"如何在这个仓库里做代码审查"或"如何运行测试套件并修复失败"。

MCP 的优势​

MCP 服务器则提供了一组不同的能力：

  • 有状态的交互：MCP 服务器可以在多次工具调用之间保持状态（比如 OAuth 令牌缓存、数据库连接池）
  • 结构化的工具接口：工具的 schema 是类型安全的，参数验证由协议保证
  • 实时通信：支持双向通信，服务器可以主动通知客户端
  • 组合性：多个 MCP 服务器可以同时连接，Agent 可以跨服务器组合工具
  • 安全性：认证、授权在协议层面定义，不是事后补丁

为什么我仍然偏好 MCP​

1. 类型安全与验证

Skills 依赖自然语言描述来告诉 Agent 如何使用工具。如果描述有歧义，Agent 就会用错。MCP 的工具 schema 是机器可验证的——参数类型、必需 vs 可选、枚举值都在 schema 里，Agent 不需要猜。

2. 可组合性

在真实项目中，你可能需要同时访问 GitHub、数据库、Slack 和内部 API。每个都做成一个 Skill 文件会很快变成维护噩梦。MCP 服务器可以独立开发、独立部署、独立版本管理，然后通过配置组合在一起。

3. 状态管理

很多真实工具需要状态——OAuth 令牌需要刷新、数据库连接需要复用、缓存需要失效策略。Skills 是无状态的（每次调用从零开始），而 MCP 服务器是长期运行的有状态进程。

4. 错误处理

MCP 工具返回结构化的错误，Agent 可以据此决定是否重试。Skills 中的脚本错误通常是退出码或 stderr，不够结构化。

什么时候用 Skills​

尽管我偏好 MCP，Skills 在以下场景仍然更好：

  • 编码工作流：多步骤的代码操作流程（如"审查 PR → 修复 lint → 运行测试"）
  • 仓库特定知识：这个仓库的测试怎么跑、lint 规则是什么、哪些目录不能碰
  • 一次性任务：不值得写一个完整服务器的简单工具

结论​

Skills 和 MCP 不是互斥的——它们是互补的。Skills 适合编码工作流和仓库知识，MCP 适合外部工具集成和有状态的交互。但如果你要构建一个生产级的 Agent 系统，MCP 的类型安全、可组合性和状态管理能力使它成为更可靠的选择。
