## 中文翻译

### 分层代码审查与基于风险的人类监督

AI 代码审查不是一次性的"让 AI 看看 diff"——它应该是一个分层系统，每一层负责不同类型的问题，只在需要人类判断时才把人拉进来。

#### 为什么要分层

单一的 AI 审查 Agent 面临两个矛盾的需求：

1. **覆盖面**：需要检查安全、性能、风格、正确性、可访问性……
2. **深度**：每个维度都需要深入分析，而不是表面扫描

一个 Agent 试图做所有事情，结果是什么都做得不深。分层架构通过将审查拆分为多个专门的 Agent 来解决这个矛盾。

#### 分层架构

**第一层：自动化检查（无需 AI）**

在 AI 审查之前，先运行确定性工具：
- Linter（ESLint、Ruff、Semgrep）
- 类型检查器（TypeScript、mypy）
- 静态分析（SonarQube）
- 测试套件

这一层过滤掉大量低级问题，让 AI 审查可以专注于更复杂的问题。

**第二层：AI 快速扫描**

一个快速的 AI Agent 做广度扫描：
- 变量命名是否一致
- 是否有明显的不安全模式（如 SQL 注入）
- 是否缺少边界检查
- 代码风格是否符合项目约定

这一层的目标是快速、低成本、高覆盖率。

**第三层：专业审查 Agent**

针对高风险变更，启动专门的审查 Agent：
- **安全审查 Agent**：专注于输入验证、认证绕过、权限提升
- **性能审查 Agent**：分析 N+1 查询、内存泄漏、不必要的重新渲染
- **架构审查 Agent**：检查是否违反了项目的分层约定
- **可测试性审查 Agent**：评估新增代码是否可测试

**第四层：基于风险的人类监督**

不是所有 PR 都需要人类审查。基于以下因素决定是否需要人类审查：

- **变更范围**：影响了多少行、多少文件
- **变更区域**：是否触及安全敏感代码、支付逻辑、核心架构
- **AI 置信度**：AI 审查是否标记了不确定的问题
- **作者经验**：新成员的 PR 可能需要更多人类审查

#### 基于风险的人类监督

传统做法是"每个 PR 都需要至少一个人类 approve"。这在高风险变更中是合理的，但对于低风险变更（如文档更新、测试补充、依赖升级）是浪费人类时间。

基于风险的监督模型：

| 风险等级 | 示例 | 审查方式 |
|---|---|---|
| 低 | 文档更新、注释补充 | AI 审查即可 |
| 中 | 新增 API 端点、UI 调整 | AI 审查 + 人类快速过目 |
| 高 | 认证逻辑、支付流程、架构变更 | AI 审查 + 人类深度审查 |

这种分级不是在削弱人类审查——而是在让人类把注意力集中在最重要的地方。

#### 实施建议

1. **从第二层开始**：先部署一个通用的 AI 审查 Agent，获得快速价值
2. **逐步添加专业层**：根据实际遇到的问题，添加专门的安全、性能审查 Agent
3. **校准风险模型**：跟踪 false positive 和 false negative，调整风险分级阈值
4. **保持人类在环**：AI 审查是增强人类审查，不是替代

#### 结论

分层代码审查不是一个工具——它是一个系统。通过将不同类型的审查分配给最合适的执行者（工具、AI 或人类），你可以在提高审查覆盖率的同时减少人类的负担。关键是将人类审查从"每个 PR 都看"转变为"只看需要人类判断的 PR"。
