## 中文翻译

### 打造符合人机工程学的仓库

"人机工程学"通常用于物理产品设计——椅子的高度、键盘的角度、屏幕的距离。但代码仓库也有人机工程学，而且随着 AI Agent 成为主要"用户"，仓库的人机工程学变得前所未有地重要。

#### 谁是仓库的"用户"

传统上，仓库的"用户"是人类开发者。但现在，Agent 也是用户——而且它阅读代码的方式和人类完全不同：

- 人类用模式识别和领域知识导航代码
- Agent 用上下文窗口和工具调用来导航代码
- 人类可以容忍模糊性，Agent 不能
- 人类会跳过不相关的代码，Agent 需要明确的信号知道什么不相关

一个"符合人机工程学"的仓库，是指同时为人类和 Agent 优化了导航和操作体验的仓库。

#### 人机工程学设计原则

**1. 降低认知负荷**

- 文件应该足够小，让 Agent 能在一个上下文窗口内完整理解
- 函数应该做一件事，名字应该说明那件事是什么
- 避免"魔术"——隐式的全局状态、运行时修改的类、不明显的副作用

**2. 快速反馈循环**

Agent 依赖反馈来验证它的操作。一个符合人机工程学的仓库有：
- 快速的测试套件（秒级，不是分钟级）
- 快速的 lint（即时反馈）
- 清晰的错误信息（不是深埋在日志中的堆栈跟踪）

**3. 一致性**

- 同类文件应该有相同的结构（所有路由文件看起来一样）
- 命名约定应该一致且可预测
- 错误处理模式应该统一

**4. 自文档化**

- 文件名应该说明内容是什么
- 目录结构应该反映架构决策
- 类型注解和接口定义应该足够完整，不需要读实现就能理解用法

**5. 可发现性**

- 入口点应该明显（`main.py`、`index.ts`）
- 配置应该集中（不是散落在多个文件中）
- 依赖关系应该明确（不是通过运行时动态导入）

#### 反模式

以下是一些降低仓库人机工程学的常见反模式：

| 反模式 | 问题 | 替代方案 |
|---|---|---|
| 巨型文件（5000+ 行） | Agent 无法完整加载 | 按功能拆分 |
| 动态导入 | Agent 不知道依赖关系 | 用静态导入 |
| 隐式配置 | Agent 不知道需要什么环境变量 | 集中配置 + `.env.example` |
| 没有测试 | Agent 无法验证修改 | 至少覆盖关键路径 |
| 不一致的命名 | Agent 需要猜测约定 | 统一命名规范 |

#### 评估你的仓库

问自己这些问题：

1. 一个新来的 Agent 能在 5 分钟内知道怎么运行测试吗？
2. Agent 能在不读全部代码的情况下理解某个函数的输入和输出吗？
3. 当 Agent 修改一个文件，它能在 30 秒内得到测试反馈吗？
4. Agent 能从文件名和目录结构推断出项目的架构吗？

如果任何回答是"否"，你的仓库还有改进空间。

#### 结论

仓库的人机工程学不是奢侈——它是生产力倍增器。一个符合人机工程学的仓库让人类开发者更高效，让 Agent 更准确，让整个团队更快地交付价值。在 Agent 时代，仓库的人机工程学不再是可选项。
